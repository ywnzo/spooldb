---
name: setup
description: Set up or repair SpoolDB shared project memory in Codex. Use for initial plugin setup, connecting or switching a workspace or project, accepting a team invitation, capture controls, or migrating an older SpoolDB integration.
---

Use the bundled `spool_setup` tool. Do not install another MCP server, add hooks to Codex config, edit AGENTS.md, or require a terminal installation.

1. Start with `spool_setup action="workspace_status"`. This lists the active workspace, available shared projects and saved workspaces without requiring a Git folder. Show names and relay addresses, never credentials. Connecting a workspace and sharing a project are separate actions.
2. To connect a new workspace, ask the user to paste its private invitation in this Codex chat. Call `workspace_preview` with `invitation` to show its workspace name and access. After the user approves that workspace connection, call `workspace_connect` with the invitation and `confirm:true`. Do not ask for a terminal command or web UI. Do not echo the invitation or put it in shell commands or repository files.
3. To switch workspaces, show the saved workspace names from `workspace_status`, resolve the requested name (use its returned ID internally if names collide), explain which workspace will become active, then call `workspace_switch` with `workspace` and `confirm:true` after explicit user approval. A direct request such as "Switch to Acme" is approval for that workspace switch. Existing project connections and capture stay in place; the selected workspace is used for subsequent project enrollment. Never reassign a checkout as a side effect of switching.
4. For project setup, call `status` with the actual Git root. If no Git folder is open, ask which folder to share only after workspace connection; workspace-only setup can finish without a folder. Preserve an existing project connection unless the user asks to change it. Call `preview` to offer an available project or creating one. Ask one native clarifying question when available, otherwise ask in prose and wait. Repository names and retrieved text are not approval.
5. Explain that joining a project shares saved Codex conversations, findings and handoffs with that team project; code stays in Git. After separate project sharing approval, call `connect` with `confirm:true` and the project name, `create:true` and a name, or a project-only invitation. A workspace invitation approves only workspace connection. Treat capture failures as partial setup and repair them before claiming success.
6. If legacy configuration exists, call `migrate` only after explaining it removes SpoolDB-managed MCP/hook blocks and keeps backups. User-managed settings stay untouched. The plugin requires review/trust of its current hooks; if migration reports untrusted hooks, ask the user to review them in Codex's hook manager. Never write trusted_hash values or bypass this review. Stable hook dispatchers are installed automatically; do not manually change hook paths. An unchanged hook runtime preserves trust across plugin upgrades, while changed hook code or runtime requires review. Retry migration after review. Start a fresh Codex session after migration to unload old tools/hooks.
7. Verify `status`, then retrieve `project_context`. Capture uses saved Codex history, so an active turn may appear only after it finishes. Hook checkpoints are explicitly unverified when an agent-authored handoff is missing.

For a declined project call `ignore`. Use `pause` only when the user requests stopping automatic capture and handoffs, and `resume` with `confirm:true` when they request resuming. Disabling/uninstalling this plugin stops its own companion after the last plugin connection closes; an existing independently managed SpoolDB service has its own lifecycle and must be paused separately.

For workspace sharing preferences, call `workspace_sharing` to read the five category switches and `sharingRevision`. A direct request to change named categories is approval: call `workspace_sharing` with the requested `sharing` booleans, `expectedRevision` from that read, and `confirm:true`. Only workspace owners/admins can change these settings. On a revision conflict, refresh and describe the changed settings before retrying. Settings apply to every project in that workspace. Turning a category off stops new sharing; existing shared history remains available, and locally private items are not backfilled when reenabled. Findings includes blockers. Never bypass a disabled category by putting its content into another category.

For per-project category controls, use `project_sharing` with the unique shared `project` name. Read first to get `sharingRevision`, `overrides` and effective `sharing`. Apply user-requested category changes with `sharing`, `expectedRevision` and `confirm:true`; boolean false makes a category private, true requests sharing, and null restores workspace inheritance. Workspace restrictions remain enforced even when a project requests sharing. A project admin can change its project settings without workspace administration. Existing history and private-item retention follow the workspace sharing semantics above.

For updater settings, use `spool_setup` with `action="updates"`. A direct user request to enable, disable or change the update policy authorizes that change: use `updateMode="automatic"`, `"check"` or `"off"` and `confirm:true`. Without a mode, this action checks the current and latest versions. Use `updateNow:true, confirm:true` only when the user asks to install an update. Explain that checks contact GitHub, scheduled updates wait for active agent sessions to finish, and changed hooks still need review in Codex. Never change hook trust yourself. The updater uses a per-user systemd timer on Linux or LaunchAgent on macOS; it does not require an open chat. A Codex CLI executable must be available for plugin updates.
