# SpoolDB audit — 2026-10-26

Baseline: commit `71be31b`, release v0.4.32. Fixes described below are in the working tree and have not been released or deployed.

## Scope and evidence

Reviewed native/Cloudflare relay authorization and ingestion boundaries, shared/private memory handling, embedding configuration, provider switching, semantic scheduling and indexing, recent idle-sync changes, maintenance controls, and retrieval evaluation coverage. Read production health and owner status only; no production memory or configuration was changed. Reproductions use synthetic in-memory stores and disposable local relays.

Production reported v0.4.32, healthy, automatic updates enabled, no recovery needed, and no backup/artifact cleanup errors. Cloudflare BGE-M3 was configured and ready. Supported GET /healthz returned HTTP 200 with no-store and nosniff headers.

Fresh `bun audit` checked 166 packages and reported no known vulnerabilities. This does not assess the VPS OS or every native library inside its image. After fixes: 286 passing tests, 2 environment-dependent skips, public-adapter type checks passed, and git diff whitespace checks passed. Container/Caddy runtime checks were not rerun during this audit. The existing typecheck command checks public adapter types, not all implementation JavaScript.

## Reproduced defects and fixes

All three initial regression tests failed against the baseline before their fixes. The chunk-budget issue was confirmed from the loop and a separate bounded/resumable regression was added.

| Priority | Finding | Consequence | Fix |
| --- | --- | --- | --- |
| P2 | The background timer skipped an indexing retry during cooldown and did not schedule another attempt. | A transient embedding outage could leave pending memory unindexed until another request or write woke it. | Record cooldown before rescheduling; schedule the next attempt after cooldown, including when a timer was already armed. |
| P2 | Cached semantic queries awaited the background indexing job. | Existing searchable evidence fell back to keyword-only results while new inference was blocked. | Search valid existing vectors using the cached query immediately; keep backlog indexing in the background. If all vectors were cleared, rebuild them before claiming semantic readiness. |
| P2 | Provider replacement did not recheck its configuration generation after asynchronous close/dispose boundaries. | A superseded replacement could temporarily publish an obsolete index. Provider selection should not depend on timing. | Recheck generation after each relevant await; dispose obsolete replacements before installation. |
| P2 | The indexing budget was checked between records, not within one record. | An allowed 500,000-character message yields 834 passages. One record could exceed the intended 64-passage work budget and delay other work. | Enforce the budget per batch and persist an atomic partial-index cursor. Resume after restart without re-embedding completed batches. Deletion clears both vectors and partial cursors. |

## Improvements in recommended order

### 1. Explain usage and enforce budgets

Add redacted counters for requests by purpose, embedding batches/text volume, cache hits, retries, indexing backlog, and latency. Display them in Search & memory and expose the same statistics through CLI/API. Distinguish provider warm/connection status from current indexing errors: the settings status is currently based on successful activation and does not describe every later failure.

Add persisted per-relay/project ingestion and embedding usage limits, with owner controls and clear fallback behavior. The current queue and body limits bound individual work and concurrency; they do not impose a daily usage or monetary spending cap. An authorized writer can still create substantial retained data and embedding work. Counting requests alone cannot enforce an exact provider currency budget; meter text/tokens consistently and explain the approximation.

Acceptance: an idle day has a measured request count; ordinary capture accounts for every outbound batch; a configured limit prevents further external work without losing local writes; settings report when and why keyword fallback occurred. Do not retain request text or credentials in telemetry.

### 2. Measure usefulness before adding retrieval features

The retrieval benchmark currently has eight synthetic questions and twenty records. That is useful as a smoke check, but insufficient evidence of production relevance or total agent-token savings.

Expand to a versioned set of realistic, sanitized English/Czech questions covering exact identifiers, paraphrases, multiple projects, stale/superseded findings, Git mismatches, ambiguous questions and questions with no relevant answer. Evaluate local and Cloudflare embeddings on the same corpus. Measure recall/MRR, irrelevant context returned, context size, latency, and fresh-chat continuation success. Use an approved synthetic/sanitized corpus; this audit did not upload company history for evaluation.

Acceptance: a release gate flags a relevance regression, and each returned context card helps an agent answer or resume a defined task. Add reranking only if measured benefit justifies its latency and external processing.

### 3. Separate latency-sensitive queries from indexing and measure vector scale

Cached queries no longer wait for indexing, but a new query can still wait behind serialized embedding work. Give bounded query work priority over bulk indexing, with cancellation and deduplication, while preserving provider concurrency limits.

Vector search currently materializes and scores all eligible vectors in JavaScript using exact cosine distance. The candidate result cap limits returned results, not the number of vectors scanned. Benchmark 10k/100k vectors for both 384- and 1024-dimensional models, event-loop delay, peak memory and concurrent project queries. Select an ANN/vector indexing approach only after measuring a useful cutoff, retaining project filters and exact lexical search.

The million-operation storage workload is not proof of million-vector retrieval performance.

### 4. Strengthen recovery and release assurance

Keep rollback retention, and add a periodic disposable restore drill that checks actual memory retrieval and an already-synced client's subsequent replay. Include revocation and conversation-deletion tombstones in the recovery assertions. Never run a destructive restore against production for a drill.

Consider release attestations/signature verification as an additional integrity boundary beyond release-hosted checksums. Protect release administration separately. Current updates still trust the GitHub repository and its release administrators.

### 5. Improve maintainability incrementally

Several core modules compress large state transitions into long lines/functions. Extract tested sync policy, provider lifecycle and indexing state transitions into small readable functions as those paths change. Expand implementation-level static checks incrementally; passing the current public-adapter type check does not imply all runtime code is typechecked. Avoid a broad rewrite while behavior is still evolving.

## Security boundaries and limitations

Existing project/workspace authorization, write-policy refresh, credential redaction, no source-file uploads, private sharing behavior and deletion protections remain covered by tests. No new confirmed critical exploit was identified in the reviewed paths. This is not proof that none exists.

Remaining operational responsibilities include bearer-token revocation, protecting relay disks/backups (not application-encrypted), limiting authorized ingestion/API spend, protecting release maintainers, and treating agent memory as untrusted evidence. Raw sharing controls do not redact secrets from enabled categories. VPS OS inspection, image vulnerability scanning, independent penetration testing and production traffic attribution were outside this audit's access/scope.


## Implemented follow-up

The working tree now also includes strict 2,000-character handoffs; owner-visible self-hosted usage counters and persistent external embedding caps (UI/API/interactive CLI); a fair priority inference queue; a 50-question multilingual quality gate in release CI; and paged exact vector scoring with 10k/100k measurements at 384/1024 dimensions. See docs/memory.md and benchmarks/results/README.md for operation, measurements and remaining limitations. These changes have not been deployed.

Final full regression run: 296 passed, 2 environment-dependent skips. The local quality gate passed its measured baseline: 88.1% recall@3, 75% unrelated-query empty rate, no stale/project leaks in the fixture, and 69.1% character reduction compared with full records for the same results. The 100k/1024 paged scan peaked at about 201 MiB rather than the original 1,701 MiB. It still took roughly 1.3–1.6 seconds in the final synthetic run, so exact retrieval is not presented as an unlimited-scale solution.
